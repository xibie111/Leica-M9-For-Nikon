日期：2026-10-18。冻结基线为 `fa2e52382ed47f8a5c743c1b5c484365242faca7`；基线源码、权重指纹及全部调查数据保存在 `E:/m9output/cpu_frontend_20261018/`。

本轮没有采用线程数或条带参数调优。三轮独占 CPU 筛选未找到超过控制波动、可稳定复现的优势。产品只修复小图可能生成空 IPE 条带、线程数可能多于有效任务数的问题；普通照片的线程数、任务数、条带边界和像素算式均保持原样。不增加用户开关，不调整 OpenCV、BLAS、Torch 的全局线程设置。

## 历史波动能说明什么

调查对象是 2026-10-17 的 AB/BA/AB 三对严格速度验证。相同 arm 的前两轮与第三轮相比，多阶段同时变快，并非只有 CPU 前端变化：

| arm / 较慢轮 → 第三轮 | frontend 差额 s | total_before_publish 差额 s | frontend 占该差额 |
|---|---:|---:|---:|
| baseline 1 → 3 | 1.7003 | 56.5745 | 3.01% |
| baseline 2 → 3 | 1.2651 | 50.0802 | 2.53% |
| candidate 1 → 3 | 2.8918 | 60.8393 | 4.75% |
| candidate 2 → 3 | 2.6953 | 67.0415 | 4.02% |

这里的约 **2.5%–4.8% 是历史阶段耗时差额的占比**，不是前端占整次处理的比例，也不是本轮可获得的提速。历史 style、filter、models、jpeg 等阶段也有明显变化，单独改变前端调度不能解释大部分历史差额。

旧记录没有区间 CPU 利用率/有效频率、GPU 利用率/时钟/功耗/温度、电源状态历史及竞争进程遥测。`style` 是 CPU/GPU 混合 wall timer；`models` 包含 CPU 重建、传输/检查和哈希；`jpeg` 包含 P3、量化、OpenCV 压缩、ICC 与 EXIF。不能把这些 timer 当成单一设备内核耗时，也不能倒推出热降频、电源切换、缓存、后台程序或嵌套线程是唯一原因。

历史 runner 的 `hot_first_photo` 也不是模型常驻的热首张：它关闭预热 1628 的 session，再开启测量 session 处理 0192，需要重新加载三份模型。0398/1567/最后的 1628 才共用常驻模型。冷 1628 与首张 0192 的尺寸不同，不能直接当作同图冷/热惩罚比较。旧六个 worker 的模型加载次数、权重、成片指纹和精度设置一致，关闭后 CUDA allocated/reserved 都归零；这支持输出一致及清理有效，不证明历史波动只有一个原因。

来源：`evidence/historical_analysis_001.json`、`historical_photos_001.csv`、`historical_invariants_001.json` 和 `historical_findings_001.md`。全部旧样本均保留，没有为了结论删除慢轮次。

## 唯一产品修改：消除空任务，限制线程不超过任务

```python
n = os.cpu_count() or 4
tasks = min(2 * n, lin.shape[0])
bounds = np.linspace(0, lin.shape[0], tasks + 1).astype(int)
with ThreadPoolExecutor(min(n, tasks)) as ex:
    list(ex.map(run, range(tasks)))
```

对普通照片 `H >= 2*n`，`tasks` 仍为 `2*n`，worker 数和 `linspace` 的全部边界与基线相同。因此这不是普通照片的提速补丁。对高度少于任务数的非空输入，不再提交空切片，也不再启动多于有效任务的 workers。

原问题已在冻结基线复现：高度 1 的输入会向 IPE 提交 `(0,1,3)` 空切片；预修改记录为 8 passed / 1 expected failure，见 `prechange_regression_001.json`。修复后的调度专项为 **11 passed**，包括 main/tele、真实 AE 与 IPE 串行逐位参考、非连续/portrait 输入、输入不变性、短图与条带边界、逆序完成时逐行仅处理一次、异常后线程退出。

小图 IPE 测试用固定 AE 隔离调度问题；既有 AE 的 16×16 测光布局限制没有改变，不能把这一修复描述为完整管线已支持任意 1×1 照片。AE、ADRC/TMC、gamma、色彩/HSV/LUT 算式、float32/float64 转换、模型/权重/选择阈值、tele、EV=0、D50、EXIF、JPEG 和 JSON 默认值均未调整。

## 采样器 002：观察成本与 Windows 限制

`passive_telemetry_002.py` 在外部进程运行，不导入数值/渲染库、不初始化 CUDA、不改变电源设置。默认每 2 秒读取 GPU/系统及跟踪 PID，后台全进程 CPU 扫描间隔至少 5 秒；每个命令、扫描和样本均记录起止时钟。CIM/powercfg/初始扫描完成并输出 `READY` 后才允许释放测量 worker。

`telemetry_preflight_002.jsonl` 的短预检记录为：

- READY 前设置阶段约 **3.0040 s**，不放入正式 arm 计时；其中 CIM 命令约 1.3015 s。
- 约 4 秒预检仅有 **2 个样本**。采样 body wall 为 **65.7–71.1 ms**；GPU 查询为 **54.5–59.9 ms**，跟踪 PID 扫描为 **5.45–5.68 ms**。
- 父观察进程累计 CPU 读数为 **0.0625 s**，不包含外部命令的子进程 CPU，也没有独立的 READY 时 CPU 基线。body wall 包含等待，不能直接视为 CPU 成本或整段性能惩罚。
- 该短预检没有触发重复的 5 秒后台扫描，不能据此承诺后台扫描也只有数毫秒。正式七个 arm 统一采用 observer002、2 秒间隔、关闭后台全进程扫描；实际采样 body wall 中位数为 88.7–104.8 ms，最大 326.8 ms。查询和跟踪扫描耗时逐 arm 保留，观察器开销非零；这些 wall 延迟也不是完整的观察器 CPU 成本。

Windows 当前进程 CPU delta 未独立验证。第一轮 screen 的 `effective_cores` 甚至出现 0.0，因此这些字段仅保留作辅助观察，不能单独当成“占用了几核”或过度订阅的证明。进程 CPU 百分比以一核 100% 为基准，系统百分比按全部逻辑核计，两者口径不同；进程总线程数也不是同一时刻的活跃核数。

同样，CIM 时钟可能是名义值；GPU 遥测是整设备汇总，WDDM/进程可见性有限，`nvidia-smi` 本身也有开销。按命令/扫描区间与阶段事件做重叠关联，不能把一行所有字段当成同一瞬间，更不能据此补造昨天缺失的遥测或认定唯一因果。
